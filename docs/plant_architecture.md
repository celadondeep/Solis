# Shared plant architecture

The same planner, consumption model and dashboard code serves every site.
Each plant has independent configuration and learned state. Transport and
hardware timing are deliberately separate from energy decisions.

| Layer | Shared implementation | Per-plant data |
|---|---|---|
| Configuration | `site_registry.py`, `site_defaults.json` | `sites/<key>.json` |
| Planning | `manager.py`, `planner.py`, `horizon*`, `core.py` | Battery capacity, floors, sensors, headroom setup time |
| Execution contract | HA `custom_templates/energy_plan.jinja` | Plan and planner entities, minimum SOC |
| Transport | HA Modbus / SolisCloud executor blueprints | Entity bindings, cloud entry and serial, currents |
| Consumption | `consumption.py`, `consumption_rolling.py` | Meter, output entities, data file, timezone, window |
| Dashboard | `dashboard_template.py`, `dashboard_design.py` | Names, entities, capabilities, navigation, optional finance portfolio |
| Power quality | `power_quality_manager.py` | Measurements, sample/save intervals, learned-state file |

`profiles.py` and `power_quality_profiles.py` retain their old import contracts.
The old per-site Python wrappers remain compatible but apps.yaml now uses the
classes generated by `plant_apps.py`. Optional home battery health and weekly
report apps take a site argument. No additional notification delivery is enabled.

## Adding a plant

1. Add `energy_system/sites/<key>.json` with schema version 1. The filename
   must match `energy.KEY`. Use a unique output namespace and state filenames.
2. Configure `energy.TRANSPORT` and `execution.adapter` as `modbus` or
   `solis_cloud`. Bind real entities and verified physical limits. `$ref`
   references are local to that plant, resolve lists as well as objects and
   are deep-copied. `{apps_dir}` makes state paths portable.
3. Configure the dashboard and optional portfolio membership. Navigation is
   generated for all registered plants. Do not use a display name to choose
   behavior or infer physical capabilities from a site label.
4. Run `python -m energy_system.render_site --site <key> --output <directory>`.
   Review generated app entries, executor binding and dashboard. The renderer
   does not install or reload anything. Add the reviewed app entries and HA
   automation, then validate and deploy with a backup.
5. Run the tests. The registry rejects shared writable entities, output and
   learned-file collisions, duplicate cloud targets, bad references and
   plan/executor binding mismatches. Shared read-only forecasts are allowed.

Registering a site is configuration work; a new inverter protocol still needs
an adapter. Existing auxiliary home guards and storm scripts remain in HA's
site-specific configuration. This migration does not claim that all unrelated
HA automations are generic or that every inverter exposes the same capability.

## Rolling consumption

Default: `ROLLING_WINDOW_DAYS=30`, `TIMEZONE=Europe/Vilnius`, daily update
`00:20:00`. The window includes local date **today minus 30 through yesterday**.
Missing days do not extend it. Today, future dates, nonfinite, negative and
zero daily readings are not training observations.

Daily estimates use the arithmetic mean after isolated IQR outliers are
separated (2.5 IQR, with a relative spread floor). These are statistical
outliers, not proof of a meter defect. Weekday charts show the actual mean
and count for each weekday. Forecast weekday factors shrink towards the
common mean because a 30-day window contains only four or five examples of
each weekday. The rolling forecast does not multiply a second preset seasonal
factor into an already seasonally adapting average.

Hourly profiles use `recorder.get_statistics` with hourly energy `change`
in kWh, fetched from HA rather than from the inverter. Only complete days
enter the hourly profile. UTC coverage across local midnight correctly handles
23-hour and 25-hour DST days. Repeated local hours contribute two observations;
missing hours are not filled with zeros. Duplicate records are idempotent and
conflicting duplicate hours invalidate that day's hourly profile.

The startup/daily query has a 25-second local timeout, a 15-minute minimum
retry interval and at most one delayed 30-minute retry. Failed queries retain
cached data within the calendar window. Insufficient data retains the last
usable forecast shape while publishing `insufficient_data`; observed charts
do not masquerade as a forecast. At least five usable days are required.
No clock-setting ping, forced inverter read or new SolisCloud request is used.

`consumption_profile*` publishes window dates, daily/hourly counts, weekday
counts, excluded dates, incomplete hourly dates, source status and refresh
time. `consumption_daily_avg*` now means actual historical daily mean;
`consumption_forecast_tomorrow*` remains a forecast. Raw daily data is kept for
120 calendar days; model writes use flush/fsync and atomic replacement.

Supported APIs were verified against the installed AppDaemon 4.5.13:
[HA recorder action](https://www.home-assistant.io/actions/recorder.get_statistics/),
[AppDaemon HASS API](https://appdaemon.readthedocs.io/en/stable/HASS_API_REFERENCE.html).

## Safety and compatibility

Both executors require an actionable plan with a fresh evaluation, healthy
planner, unexpired lease and consistent power/slot targets. Cloud retains its
single outstanding write, real readback and minimum 360-second write spacing.
Modbus retains local feedback checks and rechecks the lease, storm and manual
controls after waiting for a cutoff change. Stale or inconsistent plans cannot
enable the discharge slot. Existing physical floors (home 13%, Eimo 6%) and
command setup allowances (5/30 minutes) are preserved in profile data.

The dashboards share Energy, Analysis, Payback and Consumption pages. Optional
portfolio/physical features can be omitted. Eimo's existing `/eimo` overview
path is preserved. An unchanged but freshly evaluated plan is displayed as
fresh using its renewable lease rather than its original commit timestamp.
